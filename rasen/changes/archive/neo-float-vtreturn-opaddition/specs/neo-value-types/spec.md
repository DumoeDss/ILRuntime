# neo-value-types spec delta -- neo-float-vtreturn-opaddition

## ADDED

### Requirement: Autogen Neo CLR binding marshals binder value-type params and returns

Under `ENABLE_NEO_MODE`, a CLR method whose declaring type has a registered
`ValueTypeBinder` and that takes and/or returns a binder value type BY VALUE, when invoked
from IL through its autogenerated Neo redirect (`call.redirect` -> the generated `*_Neo` stub
registered via `RegisterCLRMethodRedirectionNeo`) on the REGULAR-CALL path (a dest register
is present, so the runtime passes a non-null `retDst`), MUST marshal each by-value value-type
parameter from the callee frame region via `ILIntepreter.ReadNeoValueType` (advancing the
cursor so any following scalar param is read at the correct offset) and MUST write a value-type
return value to the caller's dest slot via `ILIntepreter.WriteNeoValueType` (sized via
`ILIntepreter.GetNeoValueTypeManagedSize`). A stub MUST NOT leave a value-type parameter as an
uninitialized `default(...)` (the args would never be read and the cursor would mis-align the
following params), and MUST NOT omit the return write (the returned struct would be discarded,
leaving the caller's dest zeroed).

The code generator (`BindingGeneratorExtensions.cs` AppendArgumentCodeNeo / the VT-return arm,
and `MethodBindingGenerator.cs` VT-`this` arm) MUST emit only PUBLIC-accessible callees in the
consumer assembly -- specifically it MUST reference `ILIntepreter.GetNeoValueTypeManagedSize`
(the public facade), NOT the internal `Optimizer` class (the consumer project has no
InternalsVisibleTo, so an internal reference never compiles). Generated binding files
committed to the repository MUST be consistent with the current generator (a stale
pre-Step-13b stub that emits `default(...)` + a `// TODO: CLR value type ... Step 13`
placeholder violates this requirement and produces a zero result).

NOTE (out of scope for this requirement): a CLR struct CONSTRUCTOR invoked via `newobj` is
lowered by the optimizer to `initobj; ldloca; push(this byref); call.redirect .ctor` with
dest=`-`, for which the runtime passes `retDst=null`; on that path the binding's
write-to-`retDst` no-ops and the constructed struct does not reach the caller. That is a
separate optimizer/runtime contract gap (communicate the struct dest), not a binding-
marshalling failure, and is tracked as a follow-up.

#### Scenario: a static op_Addition returning a binder VT
- GIVEN IL that calls `TestVector3.op_Addition(a, b)` (a 3-float struct with a registered
  binder) where `a`, `b` are host-precomputed `TestVector3.One`
- WHEN the call is JIT-lowered and executed under Neo on the regular-call path
- THEN the autogen redirect reads `a` and `b` via `ReadNeoValueType`, computes the sum, and
  writes the result via `WriteNeoValueType`, so the caller observes `(2,2,2)` (NOT zero).

#### Scenario: a binder-VT-returning property getter and a VT-param/scalar-param operator
- GIVEN IL that reads `TestVector3.One2` (a VT-returning static getter) and IL that calls
  `TestVector3.op_Multiply(a, scalar)` (a VT param followed by a scalar param)
- WHEN executed under Neo on the regular-call path via the autogen redirects
- THEN the getter writes its VT return via `WriteNeoValueType`, and the operator reads the VT
  param via `ReadNeoValueType` (advancing the cursor so the following scalar param is read at
  the correct offset) and writes its VT return, so the caller observes correct field values.
