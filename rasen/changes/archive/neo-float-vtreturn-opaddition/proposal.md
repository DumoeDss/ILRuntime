# Proposal: neo-float-vtreturn-opaddition

## Why
Child-26 (neo-ldobj-array-element) surfaced a float-struct gap it had to sidestep with an
INT struct (`NeoArrElemIntProbe`): two symptoms on `TestVector3` (3 floats, the pervasive
green-smoke float struct) --
1. `new TestVector3(float, float, float)` "yields a ZERO struct" (ctor args don't reach fields).
2. `TestVector3.op_Addition`'s float VT-return "doesn't write back".

The claim was SUSPICIOUS: children 3/8/15/16/21 all construct `TestVector3` and read its
fields and PASS. So "ctor yields zero" cannot be universal. This change pins the EXACT
trigger before fixing.

## Diagnosis (Phase 1, empirical -- 3 minimal probes, Neo, JIT-dumped)
- TC1 (ctor alone): `new TestVector3(1f,2f,3f)` -> **(0,0,0)** (host sum 0 + One's 3 = 3).
  CONFIRMED symptom 1.
- TC2 (op_Addition return alone, NO ctor dependency -- `One + One`, One is host-precomputed):
  -> **(0,0,0)** (host sum 3). CONFIRMED symptom 2.
- TC3 (array += compound): JIT-time crash ("could not find expected Push instructions for
  Call/Newobj" in LowerNeoOffsets) -- a SEPARATE JIT-lowering issue, NOT a value bug.

Both framed symptoms are REAL. The "zero" result (not bit-garbage) is the tell.

## Pinned root cause
The JIT dumps show BOTH the ctor and op_Addition route to `call.redirect` -- the
AUTOGENERATED Neo CLR binding stubs (`ILRuntimeTest_TestFramework_TestVector3_Binding.cs`,
registered because TestVector3 has a registered ValueTypeBinder). Those `*_Neo` stubs are
STALE: they predate the Step 13b generator fix and emit broken placeholders:
- `op_Addition_2_Neo`: `@a = default(TestVector3)`, `@b = default(...)` with
  `// TODO: CLR value type reflection fallback: Step 13` -- the VT ARGS ARE NEVER READ from
  the frame; and `// TODO: CLR value type return ...` -- the RETURN is never written.
- `Ctor_0_Neo`: reads the float args (x,y,z) and constructs `result_of_this_method =
  new TestVector3(x,y,z)`, then `// TODO: CLR value type return ...` -- the constructed
  struct is DISCARDED, never written to `__retDst`.

The runtime reflection-fallback path (`CLRMethod.Invoke` -> `InvokeNeoClrMethod`) is CORRECT:
it marshals VT params via `ReadNeoValueType` (ILIntepreter.Neo.cs:342-345) and VT returns via
`WriteNeoValueType` (:1129-1144) -- proven by `SumTestVector3Fields`/`NeoAssertEq` running
correctly through that path. The GENERATOR (`BindingGeneratorExtensions.cs`) is ALSO CORRECT
post-Step-13b: it emits `ReadNeoValueType` for VT params (:177-178) and `WriteNeoValueType`
for VT returns (:603). ONLY the generated test-binding FILES are stale (never regenerated).

## Why the claim looked suspicious but is real
Green smoke uses `TestVector3.One` -- a `public static TestVector3 One` field initialized in
the HOST (CLR), read by IL via `ldsfld` (precomputed bytes cross as-is). It NEVER calls the
broken ctor/op_Addition autogen stubs. The bug manifests ONLY when IL CALLS the TestVector3
ctor or op_Addition (which lower to `call.redirect` -> the stale stub). Context-specific to
the autogen-redirect path, not universal -- reconciling the suspicion exactly.

## What changes
Part A (the enabler -- a latent generator bug): the generator's Step-13b emission referenced
the INTERNAL `Optimizer` class in 5 consumer-emission sites, which NEVER COMPILED in the
consumer (ILRuntimeTestBase) -- no InternalsVisibleTo, and no regen since Step 13b. Added a
public facade `ILIntepreter.GetNeoValueTypeManagedSize` (ILIntepreter.Neo.cs, Neo-file-gated)
and repointed the 5 generator sites (BindingGeneratorExtensions.cs x4, MethodBindingGenerator
.cs x1) to it, so future regen produces compilable code.

Part B (the framed-gap fix): hand-port the stale TestVector3 `*_Neo` static stubs to mirror
the (now-compilable) generator emission -- `get_One2_0_Neo`, `op_Multiply_1_Neo`,
`op_Addition_2_Neo` (read VT param(s) via ReadNeoValueType; write VT return via
WriteNeoValueType), and `Ctor_0_Neo` (+ VT return write).

NOT FIXED (symptom 1, follow-up): `new TestVector3(float,float,float)` still yields zero. The
optimizer lowers a CLR struct newobj to `initobj; ldloca; push(this byref); call.redirect
.ctor` with dest=`-`, so the runtime passes retDst=null (ILIntepreter.Neo.cs:3079) and the
ctor's write-to-retDst no-ops. This is a distinct optimizer/redirect contract mismatch (the
struct dest is communicated via the `this` byref, not retDst), separate from the regular-call
VT-return path. Diagnosis + JIT dump in design.md.

Out of scope (documented): instance-method stubs (Normalize/Test, Area-4a VT-`this`); the
diagnostic TC3's JIT Push-lowering crash; full regen of all stale AutoGenerate files.

## Tractability
CLEAN for symptom 2 (the regular-call VT-return path -- the literal "op_Addition float
VT-return"): a public facade + generator repoint + 4 hand-ported stubs, all Neo-gated /
file-gated, Legacy-neutral by construction. Symptom 1 (struct newobj ctor) is a distinct,
deeper optimizer/redirect gap and is documented as a follow-up (not forced as a risky fix).

## Capability
`neo-value-types` (ADDED requirement): the autogen Neo CLR binding for a binder value type
MUST marshal VT params/returns via ReadNeoValueType/WriteNeoValueType.
